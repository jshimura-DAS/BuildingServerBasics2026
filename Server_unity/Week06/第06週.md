### 1. APIとは何か

#### 1-1. 定義
API（Application Programming Interface）は、あるプログラムが別のプログラムに対して機能を提供するための窓口である。
Web APIは、HTTP通信を使ってサーバーの機能をクライアント（Unityなど）に提供するAPIである。

#### 1-2. これまでの学習との関係
- 第03週: Flaskでルーティングを設定し、文字列（HTML）を返すサーバーを作成した。
- 第04週: 辞書をJSONに変換する方法を学んだ。
- 第05週: SQLiteにデータを保存・取得する方法を学んだ。
- 第06週: クライアントから**データを送ってもらい（POST）**、サーバー側で検証してSQLiteに保存する。

#### 1-3. GETとPOSTの違い

| 観点 | GET | POST |
| ---- | --- | ---- |
| 主な用途 | データの取得 | データの送信・登録 |
| データの位置 | URL（クエリパラメータ） | リクエストボディ |
| 今回の用途 | ランキングの取得（第09週） | スコアの登録（今回） |

### 2. API設計に関する注意事項

APIは一度公開すると、クライアント側（Unity）のコードと密接に結びつくため、後から変更しにくい。設計段階で次の点に注意する。

- **エンドポイント名は役割が分かる名前にする**（例: `/api/scores`）。
- **リクエストとレスポンスの形式を先に決める**。実装より先に仕様を文書化する。
- **サーバー側では、送られてきたデータを信用しない**。型・範囲・必須項目を必ず検証する。
- **成功時と失敗時で、HTTPステータスコードを使い分ける**（詳細は4-2）。
- **エラーの内容をクライアントが理解できる形で返す**。原因が分かるメッセージを添える。
- **1つのAPIには1つの責務を持たせる**。スコア登録とランキング取得は別のエンドポイントにする。

### 4. 仕様で確定すべき項目

API実装の前に、受け取るデータの仕様を表として明確にしておく。仕様があいまいだと、不正データの判定基準が実装者によってばらつくためである。

| 項目名 | 型 | 必須 | 範囲・制約 | 備考 |
| ---- | ---- | ---- | ---- | ---- |
| `name` | 文字列（str） | 必須 | 前後の空白を除いて1〜20文字 | プレイヤー名。前後の空白は取り除いて保存する |
| `score` | 整数（int） | 必須 | 0以上999999以下 | 負の値・小数・真偽値・文字列は不可 |

#### 4-1. 補足事項
- `name`は空文字列（`""`）や、空白のみの文字列（`"   "`）を許可しない。
- `name`の前後に空白がある場合（例: `" PlayerA "`）は、エラーにせず`strip()`で空白を取り除いて保存する。文字数の判定も`strip()`後の値で行う。
- `score`は`True`や`"100"`のような、整数以外の型を許可しない（Pythonでは`bool`が`int`の仲間として扱われる点に注意する）。
- JSON自体の形式が壊れている場合（パース不可）も、エラーとして扱う。
- 同じプレイヤー名での複数回の登録は許可する（別々の行として登録される）。

#### 4-2. HTTPステータスコードの使い分け

##### ステータスコードとは

HTTPステータスコードは、サーバーがリクエストを処理した結果を、3桁の整数でクライアントに伝えるための番号です。クライアントは、レスポンスのボディを読む前に、このコードで「成功したのか」「リクエストが悪かったのか」「サーバー側で失敗したのか」を判断できます。

##### プロトコル上の形式

HTTPレスポンスの先頭行は「ステータス行」と呼ばれ、RFC 9112では次の形式で定義されています。

- 形式: `HTTP-version SP status-code SP reason-phrase CRLF`
- `SP` は半角スペース、`CRLF` は改行（キャリッジリターン＋ラインフィード）を表します。
- `status-code` は3桁の数字、`reason-phrase` は人が読むための説明文です。reason-phraseは省略されることもあり、コードの意味を決めるのはstatus-codeです。

例:

- `HTTP/1.1 201 Created`
- `HTTP/1.1 400 Bad Request`

ステータス行の後に、ヘッダー（`Content-Type`など）と、必要に応じてボディ（JSONなど）が続きます。

##### 分類（先頭の1桁で分類）

| 分類 | 意味 | 代表例 |
| ---- | ---- | ---- |
| 1xx | 情報（処理は継続中） | 100 Continue |
| 2xx | 成功（要求を理解し正常に処理した） | 200 OK、201 Created |
| 3xx | リダイレクト（別の場所を参照する必要がある） | 301 Moved Permanently |
| 4xx | クライアントエラー（要求の内容に問題がある） | 400 Bad Request、404 Not Found |
| 5xx | サーバーエラー（有効な要求をサーバーが処理できなかった） | 500 Internal Server Error |

今回のAPIでは、2xx・4xx・5xxを中心に使い分けます。

###### 2xx番代（成功）

- サーバーがリクエストを正しく受け取り、期待どおりに処理できたことを示します。
- `200 OK`: 取得や削除などが成功した場合に使用します。
- `201 Created`: 新しいデータを作成し、その結果が保存された場合に使用します。今回のスコア登録（`POST /api/scores`）の成功時はこれを返します。

###### 4xx番代（クライアントエラー）

- リクエストの内容（データ、メソッド、形式、対象など）に問題があることを示します。
- 同じリクエストを修正せずに再送しても成功しないのが基本です。クライアント側でリクエストを修正する必要があります。
- `400 Bad Request`: JSONの形式が壊れている、必須項目がない、型や範囲が不正などの入力不備に使用します。
- `404 Not Found`: 指定したidのデータが存在しない場合に使用します。
- `405 Method Not Allowed`: そのURLでは許可されていないメソッド（GETなど）を使った場合に使用します。
- `413 Payload Too Large`: リクエストボディが設定上限（`MAX_CONTENT_LENGTH`）を超えた場合に使用します。
- `415 Unsupported Media Type`: `Content-Type`がJSONでないなど、受け付けられない形式の場合に使用します。

###### 5xx番代（サーバーエラー）

- リクエスト自体は有効であるが、サーバー側の事情で処理を完了できなかったことを示します。
- クライアントが同じリクエストを再送することで、後に成功する可能性があります。
- `500 Internal Server Error`: DBへの書き込み失敗や、プログラムの不具合など、予期しないエラーに使用します。原因の詳細はクライアントに見せすぎず、サーバー側のログで確認します。

##### ステータスコードとJSONボディの役割

- ステータスコードは「HTTPレベルの結果」を表します。
- JSONボディの `result` や `message` は「アプリケーションレベルの結果」を表します。
- 両者は併用します。例えば、登録成功時は `201 Created` と `{"result": "ok", ...}` を返し、入力不備時は `400 Bad Request` と理由を示すJSONを返します。


| ステータスコード | 意味 | 使用する場面 |
| ---- | ---- | ---- |
| `200 OK` | 正常終了 | 取得・削除などが成功したとき |
| `201 Created` | 新規作成の成功 | 新しいレコードを作成できたとき（今回のスコア登録はこちら） |
| `400 Bad Request` | クライアント側のデータ不備 | JSONが壊れている、必須項目がない、型が違う、範囲外など |
| `404 Not Found` | 対象が存在しない | 指定したidのレコードがない（問題6で使用） |
| `405 Method Not Allowed` | 許可されていないメソッド | `/api/scores`にPOST以外（GETなど）で送ったとき |
| `413 Payload Too Large` | リクエストが大きすぎる | `MAX_CONTENT_LENGTH`を超えたとき |
| `415 Unsupported Media Type` | 形式の誤り | `Content-Type`がJSONでない |
| `500 Internal Server Error` | サーバー側の予期しないエラー | DB書き込みの失敗、プログラムの不具合など |

### 5. 不適切なデータへの対処方法の検討と策定

#### 5-0. なぜ不正データへの対処が必要か

これまでの教材（Week03〜Week05）では、自分で作ったプログラムからだけリクエストが来る前提で動かしてきました。しかしAPIを公開すると、想定外のクライアントからアクセスされることを前提に設計する必要があります。

- ブラウザの開発者ツール、curl、Postman、他人が作ったプログラムなど、どのようなリクエストでも送信できる
- 仕様書どおりのデータを送るとは限らず、空、型違い、巨大な値、悪意のある文字列が届く可能性がある
- サーバー側は「クライアントは正しいデータを送るはず」と考えてはいけない

そのため、**受け取ったデータは常に信用せず、サーバー側で必ず検証する**ことが基本になります。

##### 不正データを許容した場合の危険性

| 危険 | 内容 | 例 |
| ---- | ---- | ---- |
| 不正な値の保存 | 範囲外や空の値がDBに入り、ランキングや集計が壊れる | `score` に負の値や極端に大きい値が保存される |
| プログラムの異常終了 | 型やキーの存在を確認せずに処理すると、例外でサーバーが500を返す | `name` がないのに `data["name"]` を参照する |
| 過剰なリソース消費 | 巨大なボディや大量の文字列でメモリやDBを圧迫する | 数MBの `name` を保存しようとする |
| SQLインジェクション | 文字列を直接SQLに組み込むと、意図しないSQLが実行される | 下記の例 |
| 情報漏えい | エラーメッセージに内部情報（スタックトレース、SQLなど）を含めると攻撃の手がかりになる | 500の詳細をそのままクライアントに返す |

##### SQLインジェクションの可能性

SQLインジェクションとは、利用者の入力をSQL文の一部として文字列連結すると、入力値によってSQL文の構造そのものを変えられてしまう攻撃です。

危険な例（文字列連結でSQLを組み立てる）:

```python
name = request.json["name"]
sql = "INSERT INTO scores (name, score) VALUES ('" + name + "', 0)"
cursor.execute(sql)
```

`name` に `'); DROP TABLE scores; --` が入ると、意図しないSQLが実行される可能性があります。

対策は次のとおりです。

- プレースホルダー（`?`）を使い、値をSQLと分けて渡す（Week05で学習した方法）
- 入力検証で型・範囲・文字数を確認する（このWeekの5-2以降）
- DBのエラーを詳細のまま返さず、ログに記録して500を返す

```python
cursor.execute("INSERT INTO scores (name, score) VALUES (?, ?)", (name, score))
```

プレースホルダーを使っていても、入力検証は必要です。検証は「DBを守る」だけでなく、「仕様外のデータを業務ルールで拒否する」ためにも行います。

#### 5-1. 想定される不正データ

| ケース | 例 | ステータス | メッセージ |
| ---- | ---- | ---- | ---- |
| `Content-Type`がJSONでない | `text/plain`で送信 | `415` | Content-Typeはapplication/jsonにしてください。 |
| JSONの形式が壊れている | ボディが空、カンマ不足 | `400` | JSONの形式が不正です。 |
| JSONがオブジェクトでない | `[1, 2, 3]` | `400` | リクエストボディはJSONオブジェクトである必要があります。 |
| 必須項目の欠落 | `name`がない | `400` | nameは必須です。 |
| 型の誤り | `score`が文字列`"abc"` | `400` | scoreは整数で指定してください。 |
| 範囲外の値 | `score`が`-10`や`10000000` | `400` | scoreは0〜999999の範囲で指定してください。 |
| 文字数超過 | `name`が21文字以上 | `400` | nameは20文字以内で指定してください。 |
| 空白のみの名前 | `name`が`"   "` | `400` | nameに有効な文字を入力してください。 |
| POST以外のメソッド | `GET /api/scores` | `405` | このURLでは許可されていないメソッドです。 |
| リクエストが大きすぎる | 巨大なJSON | `413` | リクエストが大きすぎます。 |
| DBの書き込み失敗 | ディスク不足など | `500` | サーバー内部でエラーが発生しました。 |

#### 5-2. 検証の順序
検証は次の順序で行うと、原因を特定しやすい。

1. `Content-Type`がJSONか（違えば`415`）。
2. JSONとして読み込めるか（パース可否）、オブジェクトか。
3. 必須項目（`name`, `score`）が存在するか。
4. それぞれの型が正しいか。
5. 値が範囲・文字数の条件を満たすか。
6. すべて通過したらDBへ保存する（保存に失敗したら`500`）。

途中で条件を満たさない場合は、その時点でエラーレスポンスを返し、以降の処理（DB保存）は行わない。

### 6. 実装方法

#### 6-1. テーブルの準備（第05週の復習）

```python
# db.py
import sqlite3

DB_PATH = "game.db"

def get_connection():
	conn = sqlite3.connect(DB_PATH)
	conn.row_factory = sqlite3.Row
	return conn

def init_db():
	conn = get_connection()
	try:
		conn.execute("""
			CREATE TABLE IF NOT EXISTS scores (
				id INTEGER PRIMARY KEY AUTOINCREMENT,
				name TEXT NOT NULL,
				score INTEGER NOT NULL
			)
		""")
		conn.commit()
	finally:
		conn.close()
```

- 接続は使い終わったら必ず`close()`する。途中でエラーが起きても閉じられるよう、`try / finally`で囲む。
- `get_connection()`は呼ばれるたびに`DB_PATH`を参照する。この性質は、8章のテストでDBを差し替えるときに利用する。

#### 6-2. バリデーション関数

```python
# validators.py
def validate_score_payload(data):
	"""検証に問題があれば、エラーメッセージの文字列を返す。問題なければNoneを返す。"""
	if not isinstance(data, dict):
		return "リクエストボディはJSONオブジェクトである必要があります。"

	# 1. 必須項目の存在
	if "name" not in data:
		return "nameは必須です。"
	if "score" not in data:
		return "scoreは必須です。"

	name = data["name"]
	score = data["score"]

	# 2. 型と文字数（strip後の値で判定）
	if not isinstance(name, str):
		return "nameは文字列で指定してください。"
	stripped = name.strip()
	if len(stripped) == 0:
		return "nameに有効な文字を入力してください。"
	if len(stripped) > 20:
		return "nameは20文字以内で指定してください。"

	# 3. 型と範囲
	if isinstance(score, bool) or not isinstance(score, int):
		return "scoreは整数で指定してください。"
	if score < 0 or score > 999999:
		return "scoreは0〜999999の範囲で指定してください。"

	return None
```

- `isinstance(score, bool)`を先に判定しているのは、Pythonでは`bool`が`int`のサブクラスであり、`isinstance(True, int)`が`True`になってしまうためである。
- `"name" not in data`は、キーが存在しないことを判定する。`{"name": null}`のようにキーはあるが値が`null`の場合は、次の型チェックで「文字列で指定してください」になる。

#### 6-3. スコア登録APIの実装

```python
# app.py
import sqlite3
from flask import Flask, request, jsonify
from db import get_connection, init_db
from validators import validate_score_payload

app = Flask(__name__)
app.config["MAX_CONTENT_LENGTH"] = 1024 * 10  # リクエストボディの上限（10KB）
app.json.ensure_ascii = False  # 日本語を\uXXXXに変換せず、そのまま返す
init_db()


def error_response(message, status):
	return jsonify({"result": "error", "message": message}), status


@app.route("/api/scores", methods=["POST"])
def register_score():
	# 1. Content-Typeの確認
	if not request.is_json:
		return error_response("Content-Typeはapplication/jsonにしてください。", 415)

	# 2. JSONのパース（壊れていればNone）
	data = request.get_json(silent=True)
	if data is None:
		return error_response("JSONの形式が不正です。", 400)

	# 3. 必須・型・範囲の検証
	error_message = validate_score_payload(data)
	if error_message is not None:
		return error_response(error_message, 400)

	name = data["name"].strip()
	score = data["score"]

	# 4. DBへ保存（接続の失敗を含め、sqlite3.Errorは500で返す）
	conn = None
	try:
		conn = get_connection()
		cursor = conn.execute(
			"INSERT INTO scores (name, score) VALUES (?, ?)",
			(name, score),
		)
		conn.commit()
		new_id = cursor.lastrowid
	except sqlite3.Error:
		return error_response("サーバー内部でエラーが発生しました。", 500)
	finally:
		if conn is not None:
			conn.close()

	return jsonify({
		"result": "ok",
		"id": new_id,
		"name": name,
		"score": score,
	}), 201


@app.errorhandler(405)
def method_not_allowed(e):
	return error_response("このURLでは許可されていないメソッドです。", 405)


@app.errorhandler(413)
def too_large(e):
	return error_response("リクエストが大きすぎます。", 413)


@app.errorhandler(500)
def server_error(e):
	return error_response("サーバー内部でエラーが発生しました。", 500)


if __name__ == "__main__":
	app.run(host="0.0.0.0", port=5000, debug=True)
```

- `request.is_json`: `Content-Type`がJSON形式かを判定する。違う場合は`415`を返す。
- `request.get_json(silent=True)`: JSONの形式が壊れている場合でも例外を発生させず、`None`を返す。
- `data["name"].strip()`で前後の空白を取り除いてから保存する（4-1の仕様）。
- 保存に成功した行の`id`は、`cursor.lastrowid`で取得できる。
- `try / except / finally`により、DBへの接続失敗や書き込み失敗（`sqlite3.Error`）は`500`で返し、接続が開いていればどの場合も閉じる。`conn = None`としておくのは、`get_connection()`自体が失敗しても`finally`でエラーにならないようにするためである。
- `app.json.ensure_ascii = False`: Flask 3.xの`jsonify`は、既定では日本語を`\uXXXX`の形式で出力する。JSONとしては正しくUnityでも読めるが、`curl`で確認するときに読みにくいため、日本語をそのまま出力する設定にしている（Flask 2.2以降。それより古い場合は`app.config["JSON_AS_ASCII"] = False`）。
- `@app.errorhandler(405)`: `/api/scores`にPOST以外で送ると、Flask標準ではHTMLの405画面になる。他のエラーと同じJSON形式にそろえている。
- `@app.errorhandler(500)`は、予期しない例外をJSON形式の`500`で返す。ただし`debug=True`の間はFlaskのデバッグ画面が優先して表示される。公開時は`debug=False`にする。
- `host="0.0.0.0"`は第03週と同じく、仮想マシンの外（Windows側）からの接続を受け付ける指定である。

### 7. テストの方法

#### 7-1. 手動でのテスト（curlコマンド）

サーバーを起動したターミナルは使用中になるため、**新しいターミナルを開いて**実行する（第03週と同様）。

```bash
python3 app.py
```

仮想マシン内のbashから送信する例:

```bash
curl -X POST http://127.0.0.1:5000/api/scores \
  -H "Content-Type: application/json" \
  -d '{"name": "PlayerA", "score": 1250}'
```

不正なデータも試し、エラーレスポンスの内容を確認する。

```bash
# 範囲外・空の名前（400）
curl -X POST http://127.0.0.1:5000/api/scores \
  -H "Content-Type: application/json" \
  -d '{"name": "", "score": -10}'

# Content-TypeがJSONでない（415）
curl -X POST http://127.0.0.1:5000/api/scores \
  -H "Content-Type: text/plain" \
  -d 'hello'

# JSONが壊れている（400）
curl -X POST http://127.0.0.1:5000/api/scores \
  -H "Content-Type: application/json" \
  -d '{"name": "A",}'

# POST以外のメソッド（405）
curl -X GET http://127.0.0.1:5000/api/scores
```

##### Windowsから送信する場合
Windows側から仮想マシンのAPIを呼ぶ場合は、`127.0.0.1`ではなく**仮想マシンのIPアドレス**を指定する（`hostname -I`で確認。第03週参照）。PowerShellでは`curl`が別のコマンド（`Invoke-WebRequest`）のエイリアスになっているため、`curl.exe`と明示すると上記と同じ書き方ができる。

```powershell
curl.exe -X POST http://192.168.xx.xx:5000/api/scores -H "Content-Type: application/json" -d "{\"name\": \"PlayerA\", \"score\": 1250}"
```

PowerShell内ではダブルクォートのエスケープが必要になる点に注意する。

#### 7-2. DBの内容の確認

```bash
python3 -c "import sqlite3; print(sqlite3.connect('game.db').execute('SELECT * FROM scores').fetchall())"
```

#### 7-3. 確認すべき観点
- 正常なデータで`201`が返り、DBに登録されるか。
- `name`や`score`が欠けたとき、`400`と「nameは必須です。」などのメッセージが返るか。
- 範囲外の値・不正な型のとき、それぞれ適切なエラーメッセージになるか。
- `Content-Type`が違うとき`415`、JSONが壊れているとき`400`、POST以外のとき`405`になるか。
- エラーメッセージの日本語が、`\uXXXX`ではなくそのまま表示されるか。
- 同じリクエストを複数回送ると、別々の`id`で登録されるか。

### 8. テストをプログラムで実行する方法

Flaskにはテスト用のクライアント（`test_client`）があり、サーバーを起動しなくてもAPIの動作を確認できる。`pytest`と組み合わせて自動テストを作成する。

#### 8-1. 準備

仮想環境を有効化した状態で実行する。

```bash
pip install pytest
```

#### 8-2. テストがDBを汚さないようにする
`app.py`をそのままテストすると、本番用の`game.db`にテストデータが書き込まれてしまう。そこで、テスト中だけDBの保存先を一時ファイルに差し替える。6-1の`get_connection()`が呼ばれるたびに`DB_PATH`を参照することを利用する。

- `tmp_path`: pytestが用意する、テストごとに作られる一時フォルダ。
- `monkeypatch.setattr`: テスト中だけ変数の値を差し替え、終了後に自動で元に戻す。

#### 8-3. テストコードの例

```python
# test_app.py
import pytest
import db
from app import app

@pytest.fixture
def client(tmp_path, monkeypatch):
	# DBの保存先を一時ファイルに差し替え、テーブルを作成する
	monkeypatch.setattr(db, "DB_PATH", str(tmp_path / "test.db"))
	db.init_db()

	app.config["TESTING"] = True
	with app.test_client() as test_client:
		yield test_client

def test_register_score_success(client):
	response = client.post("/api/scores", json={"name": "PlayerA", "score": 1250})
	assert response.status_code == 201
	body = response.get_json()
	assert body["result"] == "ok"
	assert body["name"] == "PlayerA"
	assert body["score"] == 1250

def test_register_score_strips_name(client):
	response = client.post("/api/scores", json={"name": "  PlayerA  ", "score": 100})
	assert response.status_code == 201
	assert response.get_json()["name"] == "PlayerA"

def test_register_score_missing_name(client):
	response = client.post("/api/scores", json={"score": 1250})
	assert response.status_code == 400
	body = response.get_json()
	assert body["result"] == "error"
	assert "必須" in body["message"]

def test_register_score_negative_score(client):
	response = client.post("/api/scores", json={"name": "PlayerB", "score": -10})
	assert response.status_code == 400

def test_register_score_bool_score(client):
	response = client.post("/api/scores", json={"name": "PlayerB", "score": True})
	assert response.status_code == 400

def test_register_score_name_too_long(client):
	long_name = "A" * 21
	response = client.post("/api/scores", json={"name": long_name, "score": 100})
	assert response.status_code == 400

def test_register_score_wrong_content_type(client):
	response = client.post("/api/scores", data="hello", content_type="text/plain")
	assert response.status_code == 415

def test_register_score_broken_json(client):
	response = client.post(
		"/api/scores", data='{"name": "A",}', content_type="application/json"
	)
	assert response.status_code == 400

def test_method_not_allowed_returns_json(client):
	response = client.get("/api/scores")
	assert response.status_code == 405
	assert response.get_json()["result"] == "error"

def test_japanese_message_is_not_escaped(client):
	response = client.post("/api/scores", json={"score": 1})
	# バイト列にUTF-8の日本語がそのまま含まれ、\uXXXXになっていない
	assert "必須".encode("utf-8") in response.data

def test_db_error_returns_500(client, monkeypatch):
	# DBファイルを開けない状態を作る
	monkeypatch.setattr(db, "DB_PATH", "/nonexistent_dir/test.db")
	response = client.post("/api/scores", json={"name": "A", "score": 1})
	assert response.status_code == 500
	assert response.get_json()["result"] == "error"
```

- `test_db_error_returns_500`は、`client`フィクスチャが差し替えた`DB_PATH`を、さらに存在しないフォルダへ差し替えて、DB接続の失敗を再現している。同じテスト内の`monkeypatch`は`client`と共通のものが渡され、テスト終了時にまとめて元に戻る。
- `app.py`をimportした時点で`init_db()`が1回実行され、`game.db`（空のテーブル）が作られる。テスト用のデータは書き込まれない。

#### 8-4. テストの実行

```bash
pytest -v
```

- `-v`を付けると、各テスト名と結果（`PASSED` / `FAILED`）が1行ずつ表示される。
- テストファイル名は`test_`で始める、またはテスト関数名を`test_`で始める必要がある（pytestの命名規則）。

#### 8-5. ブラウザからHTMLでテストする

`curl`や`pytest`はコマンドライン上の検証だが、ブラウザから直接アクセスして動作を確認したい場合もある。ブラウザは基本的に`GET`しか送れないため、`POST`を送るには何らかの仕組みが必要になる。

##### 方法の候補と比較

| 方法 | 概要 | 長所 | 短所 |
| ---- | ---- | ---- | ---- |
| HTMLの`<form>`（`enctype`はフォーム形式） | ブラウザ標準機能でPOSTを送信 | JavaScript不要、最も簡単 | 送信データがJSONではなく`form`形式になるため、今回のAPIでは`415`になる |
| JavaScriptの`fetch()` | JavaScriptからJSON形式でPOSTを送信 | 今回のAPI仕様（JSON）のままテストできる | ブラウザでJavaScriptが有効である必要がある |
| JavaScriptの`XMLHttpRequest` | `fetch()`より古いAPI | 対応ブラウザが非常に広い | 記述がやや冗長 |

今回のAPIは`Content-Type: application/json`を前提としているため、**JavaScriptの`fetch()`を使う方法を採用する**。HTMLの`<form>`だけではJSON形式の送信ができない点に注意する。

##### テスト用HTMLの例

```html
<!-- test_scores.html -->
<!DOCTYPE html>
<html lang="ja">
<head>
  <meta charset="UTF-8">
  <title>スコア登録APIテスト</title>
</head>
<body>
  <h1>スコア登録APIテスト</h1>

  <label>APIのURL: <input id="url" type="text" size="40" value="http://127.0.0.1:5000/api/scores"></label><br>
  <label>name: <input id="name" type="text" value="PlayerA"></label><br>
  <label>score: <input id="score" type="number" value="1250"></label><br>
  <button id="submit">送信</button>

  <h2>結果</h2>
  <pre id="result"></pre>

  <script>
    document.getElementById("submit").addEventListener("click", async () => {
      const url = document.getElementById("url").value;
      const name = document.getElementById("name").value;
      const score = Number(document.getElementById("score").value);
      const result = document.getElementById("result");

      try {
        const response = await fetch(url, {
          method: "POST",
          headers: { "Content-Type": "application/json" },
          body: JSON.stringify({ name: name, score: score }),
        });

        const body = await response.json();
        result.textContent =
          `status: ${response.status}\n` + JSON.stringify(body, null, 2);
      } catch (error) {
        result.textContent = "通信に失敗しました: " + error;
      }
    });
  </script>
</body>
</html>
```

##### 使い方と注意点
1. `test_scores.html`をWindowsのブラウザで開く。
2. APIのURLの欄を、サーバーの場所に合わせて書き換える。サーバーが仮想マシン上にある場合は、`127.0.0.1`ではなく**仮想マシンのIPアドレス**にする（例: `http://192.168.xx.xx:5000/api/scores`）。
3. Flaskサーバーを起動した状態で「送信」ボタンを押す。
4. 入力欄の値を書き換え、正常系・異常系（空文字、範囲外の値など）を試す。

##### CORSについて
ブラウザは、読み込んだページとは異なる場所（ホスト・ポート）のAPIへ`fetch()`すると、**CORS（Cross-Origin Resource Sharing）**の制限により、サーバーが許可していない限りレスポンスを受け取れない。`file://`で開いたHTMLのOriginは`null`として扱われ、別のサーバーへのアクセスは、そのままでは**必ず**この制限にかかる。

対処法は次のいずれかである。

1. `flask-cors`を導入してAPIサーバー側で許可する（学習用）。

```bash
pip install flask-cors
```

```python
# app.py に追加
from flask_cors import CORS

app = Flask(__name__)
CORS(app)  # 全てのOriginを許可（学習用。公開時は許可するOriginを限定する）
```

2. HTMLファイルをFlaskから配信し、APIと同じOriginにする。

`CORS(app)`は全Originを許可する設定であり、公開環境では推奨されない。なお、Unityの`UnityWebRequest`はブラウザではないため、CORSの制限は受けない（第07週）。

#### 8-6. POSTリクエストが同時に多重に来た場合の検討

##### 何が起こるか
Flaskの開発サーバー（`app.run()`）は、バージョン1.0以降はデフォルトでマルチスレッド（`threaded=True`）で動作する。ただし、本番用サーバーに比べて同時処理の能力は限られており、負荷に対する安定性も保証されていない。複数のリクエストがほぼ同時に届くと、次のような状態が起こりうる。

- 処理が重なり、応答が遅くなる。
- SQLiteはファイルベースのデータベースであり、書き込みは同時に1つしか行えない。書き込みが集中すると、一時的に`database is locked`エラーが発生する場合がある（`connect()`の`timeout`で待ち時間を設定できる。第05週参照）。

##### サーバーの機能として問題になるか
今回の`INSERT`処理は1行を追加するだけの短い処理であり、通常の授業・検証規模（数人〜数十人が同時にアクセスする程度）では大きな問題にはなりにくい。ただし、次の点は仕様として考慮しておく必要がある。

| 観点 | 内容 | 対応の要否 |
| ---- | ---- | ---- |
| データの重複 | 同じ内容を2回送信すると、2件登録される | 今回は「同じ名前でも複数回登録可」を仕様とするため対応不要（必要であれば一意制約で対応） |
| 書き込み競合 | 大量の同時書き込みで`database is locked`が発生しうる | 今回の規模では許容。発生した場合は`500`を返す（6-3）。本番運用では対応を検討 |
| idの重複 | 主キー（`PRIMARY KEY`）により、同時アクセス時も同じidが重複して登録されることはない | 対応不要。なお`AUTOINCREMENT`は、削除したidの再利用を防ぐ指定である |
| 応答の遅延 | 開発サーバーは大量の同時処理を想定していない | 授業の検証規模では許容。公開運用する場合は本番用サーバーの利用を検討 |

##### バッファオーバーフローなどメモリ関連の可能性
C言語などとは異なり、PythonやFlaskは配列の範囲外アクセスを直接行えないため、古典的な「バッファオーバーフロー」は原則として発生しない。ただし、同時多重アクセスに関連して、次のような**リソース枯渇（DoS的な状態）**は起こりうるため、仕様上の考慮事項として整理しておく。

| 観点 | 内容 | 対応の要否 |
| ---- | ---- | ---- |
| リクエストボディの肥大化 | 非常に大きなJSON（巨大な`name`文字列など）を送り続けられると、メモリやディスクを圧迫する | `MAX_CONTENT_LENGTH`でリクエストサイズの上限を設定する（6-3で設定済み。超過時は`413`） |
| 大量リクエストの連続送信 | 同時・連続して大量のリクエストが送られると、処理待ちが蓄積し応答不能に近づく（意図的な場合はDoS攻撃と呼ばれる） | 授業規模では考慮不要。公開運用時はレート制限（リクエスト数の制限）の導入を検討 |
| SQLiteの同時書き込み | 同時書き込み要求が多いと、待ち行列が溜まり処理が遅延・失敗する | 授業規模では許容。将来の拡張時にMySQL等へ移行を検討 |

##### 仕様に明記しておくこと
- 「同一プレイヤー名の重複登録を許可するか」を仕様として明記する（本授業では許可する）。
- 本番相当の運用を行う場合、開発サーバーではなく`gunicorn`等の本番用WSGIサーバーを使うことを前提条件として明記する。
- 大量アクセスが見込まれる場合は、SQLiteではなく複数接続に強いデータベース（MySQL等）への移行を将来的な課題として記載する。

今回の授業規模では、追加の排他制御なしでも機能上の問題はないと判断してよい。ただし、「今後の拡張時に検討すべき事項」として仕様書に残しておくことが望ましい。

### 9. 理解度確認問題

##### 問題1（選択）
スコア登録APIのエンドポイントとして、最も適切なものを1つ選べ。また、他の選択肢が不適切な理由を述べよ。

- A: `GET /api/scores`
- B: `POST /api/scores`
- C: `GET /scores/delete`
- D: `POST /score?name=A&score=100`

##### 問題2（対応）
次の状況に対して、返すべきHTTPステータスコードを答えよ。

1. 正常にスコアを登録できた。
2. `name`が送られてこなかった。
3. `score`が範囲外の値だった。
4. `Content-Type`が`text/plain`で送られてきた。
5. DBへの書き込み中に`sqlite3.Error`が発生した。

##### 問題3（記述）
なぜサーバー側で受け取ったデータの型や範囲を検証する必要があるのか、理由を説明せよ。

##### 問題4（穴埋め）
次のバリデーション関数の空欄を埋めて、`score`が整数であり`bool`ではないことを判定するコードを完成させよ。

if isinstance(score, ___) or not isinstance(score, ___):
	return "scoreは整数で指定してください。"
```

##### 問題5（間違い探し）
次のコードは、`name`の仕様（前後の空白を除いて1〜20文字、文字列であること）を満たしていない。不足している判定を2つ挙げ、コードを修正せよ。

def validate_name(name):

		return "nameが長すぎます。"

```

##### 問題6（プログラミング）
`app.py`に、次のエンドポイントを追加せよ。
